# Architecture

## Principle: run, then narrate

The Flow never lets an LLM produce a number or a data file. Every stage first runs a seeded,
unit-tested Python step from `olist_core` (no CrewAI import) that writes the artifacts with template
narratives. Then the crew for that stage runs:

- **Tool-bearing agents** call read-through tools that return the computed results as JSON
  (`result_as_answer=True`, so the JSON reaches the next task unchanged).
- **Tool-less narrator agents** turn those results into structured narratives
  (`output_pydantic`). Gemini only returns reliable structured output from agents without tools.
- Code re-renders the narrative files: tables and numbers from code, prose from the narrator.
  Contract assumptions and model-card ethics keep the template items and append the LLM's.

Consequences: gates never depend on LLM behaviour; `--no-llm` produces spec-complete artifacts; an
LLM failure degrades one narrative to its template instead of breaking the run.

## Flow

The interactive diagram generated by CrewAI is in `docs/flow_plot/olist_flow.html`; its structure
is in `docs/flow_structure.json`.

| Step | Decorator | What it does | Routes |
|---|---|---|---|
| `prepare_run` | `@start()` | creates run folders, writes `run_status.json` | |
| `check_inputs` | `@router` | raw files vs sha256 manifest, raw schema, lookup, API key in LLM mode; on resume, re-runs the relevant gate | `inputs_ok`, `contract_ok`, `features_ok`, `failed` |
| `run_analyst_stage` | `@listen("inputs_ok")` | pure analyst stage, then Crew 1 narrates | |
| `gate_contract` | `@router` | 21 checks of `clean_data.csv` against `dataset_contract.json`; logs the HANDOFF digest | `contract_ok`, `failed` |
| `run_feature_phase` | `@listen("contract_ok")` | pure feature stage (re-validates the handoff), then Crew 2 phase 1 | |
| `gate_required_features` | `@router` | 13 checks: required present, forbidden absent, checkout-only sources, split, nulls, contract hash | `features_ok`, `failed` |
| `run_modeling_phase` | `@listen("features_ok")` | pure training and evaluation, then Crew 2 phase 2 | |
| `gate_artifacts` | `@router` | 9 checks: 8 spec files, model loads and predicts, >= 2 variations vs baseline, card sections, contract hash consistency, text hygiene | `artifacts_ok`, `failed` |
| `promote_and_finish` | `@listen("artifacts_ok")` | validation report, status, manifest, directory-swap promotion | |
| `fail_gracefully` | `@listen("failed")` | validation report, failed status, manifest; nothing promoted | |

Every step catches its own exceptions and records them in the state; CrewAI 1.14.5 has no error
hook and `kickoff()` would otherwise raise.

## Crews

**Data Analyst crew** (`crews/data_analyst`, 6 agents, sequential)

| Task | Agent | Tool | Output |
|---|---|---|---|
| `ingest_clean_task` | Senior Data Engineer | `ingest_and_clean` | raw profile + cleaning report |
| `cleaning_narrative_task` | Data Documentation Writer | none | `CleaningNarrative` |
| `eda_task` | Retail Analytics Lead | `run_eda` | two-layer EDA summary |
| `insights_task` | Business Insights Writer | none | `Insights` |
| `contract_task` | Data Governance Steward | `draft_contract_schema` | contract draft |
| `contract_narrative_task` | Data Contract Author | none | `ContractNarrative` |

**Data Scientist crew** (`crews/data_scientist`, 5 agents, one class, two phases)

| Phase | Task | Agent | Tool | Output |
|---|---|---|---|---|
| 1 | `feature_task` | ML Feature Engineer | `validate_inputs`, `build_features` | feature spec |
| 1 | `feature_narrative_task` | Feature Reviewer | none | `FeatureNarrative` |
| gate | `gate_required_features` (Flow) | | | |
| 2 | `training_task` | ML Engineer | `train_models` | model comparison |
| 2 | `evaluation_task` | Model Reviewer | none | `EvaluationNarrative` |
| 2 | `model_card_task` | Model Card Author | none | `ModelCardNarrative` |

The scientist tasks receive the contract digest as inputs (version, sha256, row count, target,
required and forbidden features, split policy).

## Failure policy

| Event | Status / stage | Exit | Promoted |
|---|---|---|---|
| Raw file missing, hash mismatch, schema change | failed / `check_inputs` | 1 | no |
| A deterministic stage raises | failed / stage | 1 | no |
| Gemini 429 / RESOURCE_EXHAUSTED after retries | failed, `quota exhausted:` | 1 | no |
| Empty or invalid structured output, other crew error | success + `narrative_degraded` warning | 0 | yes |
| Gate fails | failed / `gate_*` | 1 | no |
| Promotion swap fails | `promotion_failed`, previous artifacts kept | 1 | rolled back |
| Unexpected exception | traceback only in `traceback.txt` | 2 | no |

Injectable faults (`--inject-fault`): `bad_input_hash` (check_inputs), `crew_error` (simulated 429),
`drop_column` and `contract_mismatch` (gate_contract), `missing_feature` and `leaky_feature`
(gate_required_features), `missing_artifact` (gate_artifacts).

## Logging

`runs/<id>/pipeline.log` (promoted to `artifacts/logs/pipeline.log`) uses a dedicated `olist` logger
with secret redaction. Line grammar:

```
RUN <id> START mode= fault= seed=        RUN <id> END status=
STAGE <name> START | END status= elapsed=
GATE <gate> <check> PASS|FAIL <detail>   GATE <gate> RESULT PASS (n/n checks)
HANDOFF analyst->scientist contract_version= contract_sha256= rows= required= forbidden=
CREW <name> START | END tokens=          TASK <name> DONE agent=
TOOL <name> START | DONE | ERROR         LLM call #n START model= / LLM call DONE tokens=
FAULT INJECTED <name>                    PROMOTE START | DONE | FAILED
```

Crew transcripts: `artifacts/logs/*_crew.json`. Status: `run_status.json` (rewritten at every stage
transition). Audit: `run_manifest.json` (git sha, package versions, BLAS, environment check, input
and artifact sha256).

## Product layer: Ops copilot, dashboard, API

The engine above publishes `artifacts/`; three channels read them, all through one risk policy
(`backend/olist_api/risk.py`, ADR-14):

| Channel | For | Where |
|---|---|---|
| **Ops copilot** | the team that operates the agents: questions about runs, gates, the model and the data; scoring a CSV, a replayed day or one order | `frontend/views/copilot.py` + `backend/olist_copilot` |
| Dashboard | business and data-science readers | the other pages of `frontend/` |
| API | other systems | `backend/olist_api` (`docs/api.md`) |

A copilot turn: the page checks the passcode and the message cap, then either answers a quick reply
from templates (no LLM) or sends the question to Gemini with eleven read-only tools (at most five
calls per turn). Tools read `artifacts/` and `runs/`, or score through the same validation and
model as the API. The answer comes back with a Sources line built from the tool calls, a flag for
any percentage the tools did not return, and, for scoring, a table and two CSV downloads (the
ranked list, and the action list with customer-message drafts).
